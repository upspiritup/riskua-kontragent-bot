# RiskUA Kontragent Bot

Telegram-бот для швидкої OSINT-перевірки українського контрагента за ЄДРПОУ. Бот збирає відкриті дані з кількох джерел, нормалізує їх, шукає ризикові сигнали і формує короткий користувацький звіт українською мовою.

Проєкт не робить юридичний висновок і не називає компанію шахрайською. Він показує ознаки ризику перед оплатою, договором або передоплатою і підказує, що варто перевірити вручну.

## Актуальний стан

- Загальний бюджет збору даних для Telegram-перевірки - до 60 секунд.
- Джерела у звіті показуються як перелік перевірених відкритих джерел із фінальним уточненням `та інші джерела`, наприклад: `Джерела: Opendatabot, YouControl, Prozorro, Судові джерела та інші джерела`.
- Prozorro працює як швидкий пошуковий скринінг: бот перевіряє до 50 результатів пошуку, підтверджує роль компанії за ЄДРПОУ в деталях закупівлі і не рахує текстові збіги як участь.
- У Prozorro розділяються ролі компанії: замовник, учасник, переможець/постачальник, сторона договору. Ризики постачальника не переносяться на компанію, якщо вона була тільки замовником.
- Prozorro.Sale показується тільки для підтверджених ризикових або інформаційних згадок. `Аукціон не відбувся` без вини компанії не підвищує score.
- Судовий блок показує до 3 деталізованих судових документів із посиланнями, якщо вони доступні.
- Мінімальний score для знайденої компанії - 5/100. Позитивні фінансові сигнали можуть знижувати ризик, але не обнуляють інформаційні згадки і не знижують hard-negative факти.

## Що вміє бот

- приймає ЄДРПОУ в Telegram;
- перевіряє формат ЄДРПОУ;
- шукає базові реєстраційні дані компанії;
- збирає статус, дату реєстрації, керівника, адресу, КВЕД, статутний капітал;
- шукає контакти: сайт, телефон, email;
- перевіряє судові згадки і показує не більше 3 витягнутих судових документів;
- робить швидкий Prozorro search-summary з підтвердженням ролі компанії у деталях закупівлі;
- перевіряє Prozorro.Sale на підтверджені негативні дії або банкрутні/дебіторські контексти;
- перевіряє боргові, податкові, виконавчі та банкрутні сигнали;
- аналізує фінансові показники, якщо вони доступні, зокрема динаміку власного капіталу;
- рахує risk score від 5 до 100 для знайденої компанії;
- не підвищує ризик лише через timeout, captcha, Cloudflare або недоступність джерела;
- веде діагностичний лог для розбору помилок парсингу та маршрутів запитів.

## Як працює перевірка

1. Користувач надсилає боту ЄДРПОУ.
2. `app/utils/validators.py` перевіряє, що це 8 цифр.
3. `app/bot.py` запускає основні джерела паралельно:
   - Opendatabot;
   - Clarity Project;
   - YouControl;
   - Єдиний реєстр боржників;
   - відкриті податкові дані через data.gov.ua.
4. Після базових джерел бот запускає перевірку контактів і сайту:
   - UA-REGION;
   - PRAT/PAT;
   - SMIDA;
   - Business Guide;
   - fallback-пошук через Bing;
   - перевірка домену і вмісту сайту.
5. Дані приводяться до внутрішніх моделей з `app/models/`.
6. `app/services/risk_scoring.py` зважує тільки змістовні ризикові фактори.
7. `app/bot.py` формує короткий Telegram-звіт для користувача.
8. Технічні деталі джерел і помилок залишаються в debug/internal-даних та логах.

## Зовнішні джерела

| Джерело | URL / маршрут | Для чого використовується |

| Clarity Project | `https://clarity-project.info/edr/{edrpou}` | реєстраційні дані, податковий борг, борг ЄСВ, виконавчі провадження, банкрутство, санкції, контактні фрагменти |
| YouControl | `https://youcontrol.com.ua/catalog/company_details/{edrpou}/` | додаткове підтвердження статусу, контакти, судові згадки, ризикові сигнали |

| ДПС / data.gov.ua | `https://data.gov.ua/dataset/0e347d45-4db5-44ee-a14a-533d7cf17d7b` | відкритий набір щодо податкового боргу |
| ДПС / data.gov.ua | `https://data.gov.ua/dataset/db391c93-1e68-43c9-bd85-7c6a8427b114` | відкритий набір щодо ПДВ-реєстрації |
| UA-REGION | `https://www.ua-region.com.ua/{edrpou}` | пошук профілю компанії і контактів |
| PRAT/PAT | `https://prat.ua/reestr.php?edrpou={edrpou}`, `https://pat.ua/reestr.php?edrpou={edrpou}` | пошук сайтів акціонерних товариств, телефону, email, адреси, керівника |
| SMIDA | сайт SMIDA / профілі емітентів | пошук інформації емітента та контактних даних |
| Business Guide | бізнес-каталог | пошук профілю компанії і контактів |
| Bing Search | `https://www.bing.com/search?q=...` | fallback-пошук сайту, email, телефону і PRAT/PAT-доменів |

Деякі джерела можуть бути недоступні, повертати неповну HTML-сторінку, captcha, 403/429 або timeout. Такі випадки не вважаються ризиком самі по собі.

## Що саме збирається

### Базові дані

- назва компанії;
- ЄДРПОУ;
- статус;
- дата реєстрації;
- керівник;
- адреса;
- основний КВЕД;
- статутний капітал;
- ПДВ-статус, якщо знайдений.

### Контакти

- сайт;
- телефон;
- email;
- сторінка-джерело;
- рівень довіри до контакту: `high`, `medium`, `low`, `unknown`;
- підстава довіри, наприклад збіг ЄДРПОУ, назви, адреси або керівника на сайті.

Контактний пошук виконується незалежно по кожному джерелу. Якщо одне джерело зависло, інші не мають втрачати результат.

Timeout-и контактних джерел:

- UA-REGION: 6 секунд;
- PRAT/PAT: 8 секунд;
- SMIDA: 8 секунд;
- Business Guide: 6 секунд;
- загальний бюджет контактного пошуку: приблизно 14 секунд.

### Судові дані

Бот не трактує сире число судових згадок як кількість небезпечних справ. У звіті використовуються обережні формулювання:

- `court_mentions_count` - кількість судових згадок або документів, якщо джерело не гарантує унікальність справ;
- `court_unique_cases_count` - тільки якщо джерело реально дозволяє відрізнити унікальні справи;
- `court_risky_cases_count` - тільки якщо вдалося класифікувати зміст справ.

Якщо знайдено посилання на судові документи, бот намагається витягти коротку інформацію:

- тип документа;
- номер рішення;
- дату;
- номер справи;
- короткий висновок щодо процесуального характеру;
- ознаки стягнення, відповідальності або негативного рішення, якщо вони є.

У користувацькому звіті показується не більше 3 судових документів із посиланнями.

### Боргові і податкові сигнали

Бот шукає:

- податковий борг;
- великий податковий борг;
- борг ЄСВ;
- виконавчі провадження;
- провадження на користь ДПС або державного бюджету;
- зарплатні борги;
- стягнення коштів;
- штрафи та пеню.

Важлива рольова логіка: якщо перевіряється сам орган ДПС, бот відрізняє ситуацію, де ДПС є стягувачем, від ситуації, де з ДПС стягують борг. Фраза про те, що ДПС стягує борг з когось, не створює борговий ризик для самого органу ДПС.

### Фінансові дані

Якщо джерело містить фінансові рядки, бот намагається показати:

- дохід;
- прибуток або збиток;
- активи;
- зобов'язання;
- власний капітал;
- кількість працівників;
- зміну власного капіталу за останні доступні роки.

Якщо доступний тільки статутний капітал, бот показує його окремо і не вигадує інші фінансові показники.

### Prozorro

Prozorro-блок у звіті не починається із припущення, що всі пошукові результати належать компанії. Спершу бот підтверджує роль ЄДРПОУ у деталях закупівлі:

- `procuringEntity.identifier.id` - компанія є замовником;
- `bids[].tenderers[].identifier.id` - компанія є учасником;
- `awards[].suppliers[].identifier.id` - компанія є переможцем або постачальником;
- `contracts[].suppliers[].identifier.id` - компанія є стороною договору.

Якщо ЄДРПОУ знайдено тільки у текстовій видачі пошуку, це вважається пошуковим збігом, а не підтвердженою участю.

У звіті показуються:

- кількість результатів у пошуку;
- скільки результатів перевірено;
- скільки закупівель підтверджено як пов'язані з компанією;
- ролі компанії серед підтверджених закупівель;
- підтверджені негативні факти серед перевірених закупівель.

Score не підвищується за сам факт великої кількості закупівель, текстові збіги, участь без негативного факту або роль замовника без окремого підтвердженого порушення.

### Prozorro.Sale

Prozorro.Sale MVP шукає аукціони за ЄДРПОУ, відкриває деталі і перевіряє, чи ЄДРПОУ реально є на сторінці. Роль згадки важлива:

- банкрут / власник ліквідаційної маси;
- учасник;
- переможець;
- організатор;
- дебіторська заборгованість;
- непідтверджена або стороння згадка.

Сильний ризик створюється тільки тоді, коли негативна дія або банкрутний контекст підтверджені саме для цієї компанії: відмова від підписання, невиконання умов, дискваліфікація саме цього переможця, продаж майна банкрута або ліквідаційної маси. Якщо компанія згадується лише як дебітор у складі активів іншого банкрута, це інформаційна згадка і не означає банкрутство самої компанії.

## Risk scoring

Оцінка ризику будується на risk flags з різних джерел. Вага сигналів описана в `app/services/risk_scoring.py`.

Основні принципи:

- технічна недоступність джерела не додає ризик;
- судові згадки без аналізу змісту не дають критичний ризик;
- великі сирі числа судових згадок не показуються як прямий доказ небезпеки;
- для знайденої компанії застосовується мінімальний інформаційний floor 5/100;
- critical/high risk потребує hard-факторів або сукупності змістовних факторів;
- без hard-факту score обмежується, щоб бот не ставив 100/100 через неповні або суперечливі дані;
- конфлікт джерел не перетворюється автоматично на критичний ризик;
- позитивний висновок про відсутність податкового боргу не показується, якщо хоча б одне джерело знайшло податкове стягнення або податковий борговий сигнал.

Фінансова логіка враховує і негативні, і позитивні сигнали:

- від'ємний власний капітал, зобов'язання більше активів, збитки, слабкий публічний фінансовий профіль і дуже малий статутний капітал можуть підвищувати score;
- збиток оцінюється не тільки за абсолютною сумою, а й відносно активів, доходу та капіталу;
- прибуток, позитивний власний капітал, активи більше зобов'язань, зростання капіталу і великий дохід/активи можуть знижувати score;
- позитивний фінансовий reducer не застосовується проти банкрутства, санкцій, припинення компанії або інших hard-negative фактів.

Приклади hard-факторів:

- компанію не знайдено за ЄДРПОУ;
- компанія припинена або в процесі припинення;
- підтверджене актуальне банкрутство;
- санкції;
- значний податковий борг;
- активні виконавчі провадження;
- зарплатні борги або суттєве стягнення.

## Формат відповіді

Звичайний користувацький звіт містить:

- назву, ЄДРПОУ і короткі базові дані;
- контакти;
- фінансові дані;
- загальний ризик;
- причини оцінки;
- судові документи, якщо їх вдалося витягти;
- рекомендацію;
- джерела;
- інформаційне застереження.

Технічні статуси на кшталт `unavailable`, `not_found`, `parse_error`, `analysis_timeout` не показуються звичайному користувачу. Вони залишаються для debug/admin-режиму і логів.

## Діагностичні логи

Діагностичне логування реалізоване в `app/services/diagnostic_logging.py`.

За замовчуванням лог пишеться в:

```text
logs/riskua_diagnostic.log
```

Файл автоматично перезаписується після 2000 рядків. Це потрібно, щоб локальний лог не ріс безконтрольно.

Можна змінити шлях і ліміт через змінні середовища:

```env
RISKUA_DIAGNOSTIC_LOG=logs/riskua_diagnostic.log
RISKUA_DIAGNOSTIC_LOG_MAX_LINES=2000
```

У лог пишеться:

- маршрут перевірки;
- ЄДРПОУ;
- джерело;
- час старту;
- тривалість;
- фінальний статус джерела;
- тип помилки;
- URL без секретних query-параметрів;
- чи використовувався fallback;
- скільки контактів знайдено;
- стислий preview відповіді.

Секрети на кшталт token, api_key, password, access_token редагуються перед записом.

## Локальний запуск

### 1. Створити віртуальне середовище

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

### 2. Встановити залежності

```powershell
pip install -r requirements.txt
```

Для Єдиного реєстру боржників використовується Playwright. Якщо браузери Playwright ще не встановлені:

```powershell
python -m playwright install chromium
```

### 3. Створити `.env`

```env
BOT_TOKEN=your_telegram_bot_token
APP_ENV=local
```

### 4. Запустити бота

```powershell
python main.py
```

Альтернативно:

```powershell
python -m app.bot
```

Запуск повного набору:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Перевірка конкретного файлу:

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests\test_bot_responses.py
```

Поточний набір тестів покриває:

- парсинг Opendatabot, Clarity, YouControl, ДПС, боржників;
- контактний пошук і PRAT/PAT fallback;
- нормалізацію телефонів;
- risk scoring;
- фінальний Telegram-звіт;
- логіку судових згадок;
- недоступність джерел;
- рольову логіку ДПС як стягувача або боржника;
- debug/diagnostic logging.

## Дані, які не треба комітити

У репозиторій не можна додавати:

- `.env`;
- Telegram bot token;
- API ключі;
- лог-файли;
- `.venv`;
- `data/checks/` з runtime-історією перевірок і Telegram user id.

Ці шляхи мають бути ignored у `.gitignore`.

## Обмеження

- Відкриті джерела можуть бути неповними або застарілими.
- Частина сайтів може блокувати автоматичні запити.
- Судові згадки не дорівнюють автоматично негативному рішенню.
- Дані Clarity щодо податкового боргу можуть містити історичні записи.
- Дані ДПС після 2022 року можуть бути неповними через обмеження відкритих даних.
- Результат бота має інформаційний характер і потребує ручної перевірки перед значною передоплатою або договором.

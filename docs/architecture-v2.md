# RiskUA: технічна специфікація нової архітектури

Станом на 14.11.2026. Повний документ із обґрунтуванням, схемами та джерелами:
https://claude.ai/artifact/NMp9fGSoLyv4tZwiwj2b6v

Цей файл — коротка версія для сесій, у яких пишеться код.
Правила коду з цифрами (шари, межі розміру, тести, мережеві ліміти) — у `docs/project-rules.md`.

## Головне рішення

Бот не збирає дані наживо з чужих сайтів. Офіційні відкриті набори завантажуються
за розкладом у власну базу PostgreSQL, а перевірка контрагента — це запит до неї.
Ціль: відповідь за 1–3 секунди, жодних блокувань.

Обмеження проєкту: один VPS (2 ядра, 4 ГБ пам'яті, 40 ГБ диска), бюджет до 15 доларів
на місяць, платних API немає, розробник має до 5 годин на тиждень.

## Незмінні правила

1. Жодних запитів до сайтів-агрегаторів (Opendatabot, YouControl, Clarity), пошуковиків
   і бізнес-каталогів. Жодного браузера (Playwright видаляється).
2. Жодного обходу захисту: без ротації проксі, розв'язування капч, підробки браузера.
3. Кожне джерело йде або через `ingest/` (набір у базу), або через `sources/`
   (живий запит зі спільним HTTP-клієнтом і кешем).
4. Правила ризику — чисті функції: отримують факти, повертають прапорець або `None`.
   Вони не роблять запитів, не читають базу, налаштування і годинник.
5. Кожна зміна правил іде разом із тестом.
6. Технічна недоступність або застарілість джерела не підвищує ризик.
7. Кожен факт у звіті має джерело і дату «станом на».
8. Боржників-фізосіб у базу не зберігаємо.

## Структура коду

```text
riskua/
├── config.py      # єдине місце, де читається оточення (.env)
├── clock.py       # єдине місце, де читається поточний час
├── logs.py        # налаштування журналу
├── db/            # пул з'єднань, migrations/*.sql, увесь SQL
├── http/          # спільний HTTP-клієнт: ліміти, повтори, кеш, запобіжник
├── domain/        # чиста логіка без вводу-виводу
│   ├── models.py  # Fact, Flag, Case та коди
│   ├── edrpou.py  # перевірка коду ЄДРПОУ
│   ├── rules/     # правила ризику, модуль на групу
│   └── scoring.py # ваги та підсумковий бал
├── ingest/        # набір -> база, модуль на набір: edr, debtors, tax, vat, sanctions
├── sources/       # живі конектори: prozorro, website
├── facts/         # рядки бази -> факти, модуль на групу
├── report/        # текст звіту для Telegram, пізніше PDF
├── billing/       # етап 2: Telegram Stars, ліміти перевірок
├── usecases/      # сценарії: check_company, account, status
├── monitoring/    # етап 3: підписки на зміни
└── bot/           # обробники aiogram, клавіатури, обмеження частоти
```

Залежності йдуть згори вниз:
`bot -> monitoring -> usecases -> (billing, report, facts, sources, ingest) -> http -> (db, domain) -> (config, clock, logs)`.
Пакети в дужках один одного не імпортують. `bot` працює лише через `usecases`. `domain` не
імпортує нічого з проєкту. Модулі `ingest` і `sources` пишуть у базу й нічого не знають про бота.
Повна таблиця шарів і перевірка — у `docs/project-rules.md`, розділ 2.

Новий пакет `riskua/` створюється поруч із `app/`;
старий бот працює, доки новий не покаже той самий звіт із власної бази.

Стек: Python 3.12, aiogram 3 (long polling), httpx, psycopg 3, PostgreSQL,
Docker Compose, cron на сервері. Без Redis, Celery та ORM.

## Алгоритм завантаження набору

1. Перевірити дату або хеш файла в джерелі; якщо не змінився — вийти.
2. Завантажити файл на диск і розбирати потоком (без читання цілком у пам'ять).
3. Писати рядки в тимчасову таблицю через `COPY`.
4. Якщо рядків менше ніж 90 % від попереднього завантаження — зупинитись, сповістити адміна.
5. В одній транзакції підмінити робочу таблицю тимчасовою.
6. Записати результат у `dataset_runs`.

Запуск: `python -m riskua.ingest run <набір>` із cron. Команда бота `/status` показує
свіжість кожного набору. Якщо набір застарів удвічі проти графіка — сповіщення адміну.

## Хід перевірки

1. Перевірити ЄДРПОУ: 8 цифр і контрольна цифра (невірна цифра — попередження, не відмова).
2. Паралельно прочитати таблиці бази, зібрати список фактів.
3. Порахувати правила і бал, одразу надіслати основний звіт.
4. Блок Prozorro надіслати другим повідомленням або з кешу.
5. Зберегти перевірку зі знімком фактів у `checks`.

Сценарій перевірки живе в `usecases/check_company.py`: обробник бота лише викликає його.
Модель факту: `kind`, `value`, `source`, `as_of`, `url`. Моделі `Fact`, `Flag`, `Case` —
у `domain/models.py`; перетворення рядків бази на факти — у `facts/`.

## Правила HTTP-клієнта

- Один `httpx.AsyncClient` на процес, чесний `User-Agent` із назвою бота і контактом.
- Ліміт на хост; для Prozorro початково 2 одночасні запити і до 3 на секунду.
- На 429 і 5xx — до 3 повторів із наростаючою затримкою, `Retry-After` виконується.
- Кеш у `http_cache`: результат Prozorro для компанії — 24 години.
- Запобіжник: 5 помилок поспіль вимикають джерело на 10 хвилин.

## Що перевірити на етапі 0

1. Поля набору ЄДР: керівник, засновники, бенефіціари, дата реєстрації, статутний капітал; чи справді немає адреси і КВЕД.
2. Колонки CSV реєстру боржників: код ЄДРПОУ, категорія стягнення.
3. Точна назва параметра «Учасник» у пошуку Prozorro.
4. Формат вивантаження з реєстру санкцій (документацію API видають за запитом).
5. «Стан розгляду справ»: повний знімок чи приріст за день.
6. Структура набору фінансової звітності Держстату.

## Нові сигнали ризику з власної бази (завдання 1.11)

- одна людина керує багатьма компаніями одночасно;
- компанії менше року, а статутний капітал мінімальний;
- засновник-юрособа сам у припиненні, боржник або під санкціями;
- засновник чи бенефіціар із РФ або Білорусі;
- бенефіціара не вказано;
- керівник чи засновники змінилися останніми місяцями (історія накопичується з першого завантаження).
